# Isolated Phase 1 native resource probe

Run `powershell -NoProfile -File experiments/phase1-native-probe/run.ps1` from the repository root. This unpackaged WinUI experiment references the existing WindowsAppSDK 2.5.1 and links the exact production token/style dictionaries and icon assets. It changes no production wiring or Windows settings.

The temporary native window constructs every keyed text/button/surface/status/icon style once, retains the same control instances through Light → Dark → Light, and renders only its own harmless fixture with `RenderTargetBitmap`. Output goes to `docs/handoffs/phase1-figma-native-ui/native-resource-probe/`. Assertions check nonempty renders, actual surface pixels against required/resolved theme brushes, and all nine icon alpha edges, transparency and semantic foreground pixels. Original Close.svg is decoded natively alongside the tinted artwork, proving its fixed source stroke remains #1A1A1A across themes. A 250 ms image/font settle delay is bounded; assertions on actual pixels provide the proof. Runner metadata binds resource SHA256 values checked unchanged before/after execution.

Tint checks compare every pixel with alpha >= 64 against the expected premultiplied RGB (channel × alpha / 255, one-byte rounding tolerance). Thin antialiased source artwork can have zero alpha-255 pixels at actual 100% scale; the opaque-pixel count is informational. Startup self-checks reject a wrong theme color and transparent coverage. For a new scale, launch the built executable with a distinct `FIHLENS_PROBE_OUTPUT` path and exact-process timeout/finally cleanup to preserve earlier scale evidence; do not rerun the default runner over archived evidence.

For genuine Windows high contrast, set `FIHLENS_PROBE_REQUIRE_HIGH_CONTRAST=1` on the owned process. The fixture requires actual AccessibilitySettings.HighContrast and checks the retained controls against read-only system Window, WindowText and Highlight colors throughout all three app-theme requests. [GetSysColor](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getsyscolor) supplies the independent reference palette, using documented COLORREF byte order. The fixture never changes Windows settings; without real high contrast the required-mode run fails. RequestedTheme alone does not simulate high contrast.

For the observed two-display fixture, `FIHLENS_PROBE_REQUIRE_SCALE200=1` requires exactly one active nonprimary display with physical bounds 1920×1200, moves only the owned window there and waits for actual XamlRoot scale 2.0 before building the gallery. `AppWindow.ResizeClient` sizes 1200×960 physical client pixels; measured outer size must fit the actual work area. Actual SDK 2.5.1 secondary `DisplayArea.WorkArea` already contains desktop X/Y coordinates; native containment checks reject a different convention rather than adding the origin twice. All phases revalidate scale and display identity. No explicit RenderTargetBitmap dimensions or Windows display settings are used to simulate DPI.

At actual 200%, each of the nine base-URI production icons must render native 40×40 pixels, byte-match the same-geometry icon using an explicit original 40-pixel PNG copy, and differ from the original 20-pixel copy. `Assets/Scale100Reference` and `Assets/Scale200Reference` contain exact unchanged original bytes under unqualified filenames for this differential test; hash-check them against production before running. Reference controls overlap in a separate lower fixture row to limit height; this experimental comparison row is not production UI. DisplayArea.FindAll uses Count/index access because its WinRT IEnumerable adapter failed on the installed runtime.

Native references: [DisplayArea](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.displayarea?view=windows-app-sdk-2.0), [ResizeClient](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.appwindow.resizeclient?view=windows-app-sdk-2.0). Runtime measurements take precedence over ambiguous coordinate descriptions.

Primary API references: [RenderAsync](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.media.imaging.rendertargetbitmap.renderasync?view=windows-app-sdk-2.0), [GetPixelsAsync](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.media.imaging.rendertargetbitmap.getpixelsasync?view=windows-app-sdk-2.0), [SvgImageSource](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.media.imaging.svgimagesource?view=windows-app-sdk-2.0). Exact SDK compatibility is checked by compilation and runtime, rather than inferred from the documentation version.

`powershell -NoProfile -File experiments/phase1-native-probe/check-runner-cleanup.ps1` executes the runner's actual finally block with harmless owned child processes. Timeout, already-exited and failed-start cases verify exact-process termination and environment/location restoration. Runner cleanup kills only its retained Process instance, waits at most five seconds and disposes it, including exceptional exits.

This proves resource loading/rendering in the experiment at the recorded actual XamlRoot scale. It does not prove installed production packaging, pointer states, keyboard/Narrator behavior, genuine high contrast, other display scales, popup hosting, capture or OCR. `RequestedTheme` is an application theme change, not a Windows accessibility setting. The initial opaque-icon failure files are retained to document the defect found by real rendering.
