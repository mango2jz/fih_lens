## RALPLAN-DR (deliberate)

**Principles:** (1) Keep dependencies inward: Application → Core; Infrastructure → Application/Core; WinUI → Application/Infrastructure. (2) Prove portable behavior before relying on Windows or paid accounts. (3) Preserve cancellation and ownership semantics at each boundary. (4) Share only provider-neutral behavior; validate each untrusted provider envelope independently. (5) Use native .NET HTTP/JSON and the one justified MVVM package; avoid speculative layers.

**Decision drivers:** A working manual translator across demo and the two requested clouds; small reviewable changes with deterministic evidence; developer understanding of async UI, HTTP, JSON trust boundaries, and lifetimes.

| Viable option | Benefit | Cost / reason |
|---|---|---|
| **A — chosen:** one Application port/service, one fake, one MVVM screen, shared prompt/parser, two provider-specific adapters selected once at startup | Meets all three phases and explicit dual-provider request with one UI and no temporary screen | Two API envelopes and live verification gates increase scope; checkpoints keep it tractable. |
| B — provider-specific prompt/parser/VM paths | Each API can evolve independently with minimal shared contract coordination | Duplicates product policy and UI behavior; viable if providers later need materially different product semantics, not for current EN→VI Translate request. |
| C — single adapter first, second in a later plan | Smaller immediate integration | Does not satisfy the user's explicit both-provider scope, so not selected. |

**ADR:** Choose A. `ITranslationProvider` is justified by the external capability boundary and fake/controlled tests; the service stays a concrete direct-forwarding class. Shared `PromptBuilder` and its `TranslationInstructions` value belong to Application because they express product policy. `TranslationParser` and provider DTO/schema helpers belong to Infrastructure because they interpret untrusted wire data. These are concrete helpers, not new ports or a framework. Construct exactly one selected adapter at startup from `FIHLENS_PROVIDER_MODE=demo|gemini|deepseek` (default `demo`). No runtime selector, router, fallback, SDK, DI container, generic base adapter, retry, streaming, persistence, capture, hotkeys, OCR, Explain/CEFR live support, or extra dependency. Both cloud implementations must exist and pass offline tests even when one selected account is unavailable.

**Pre-mortem:**

1. Provider changes its model/API response → transport succeeds but parser accepts incomplete/wrong content. Mitigate with official-contract worksheet, separate envelope fixture tests, strict completion checks, byte-bound body, live smoke per provider, and a docs recheck before implementation.
2. Cancellation races with a late successful response or window close → stale result appears or shared client is disposed too early. Mitigate with token-aware fake/HTTP, one-request VM state machine, suppress late results after cancel/close, and shutdown ownership checks.
3. Credentials or Windows are unavailable → demo tests pass and the milestone is incorrectly called complete. Mitigate with independent portable/Windows/Gemini/DeepSeek gates and explicit pending evidence; never treat fake output as proof of live translation.

## Architecture and exact behavior

### Checkpoint 1 — portable foundation

Create `src/FihLens.Application/FihLens.Application.csproj` (net10.0, Core reference) and `src/FihLens.Infrastructure/FihLens.Infrastructure.csproj` (net10.0, Application/Core references); add to `FihLens.slnx` and `tests/FihLens.Tests/FihLens.Tests.csproj`. Use the existing .NET test packages. No future-feature folders.

`src/FihLens.Application/Translation/ITranslationProvider.cs` exposes one public `Task<TranslationResult> TranslateAsync(TranslationRequest request, CancellationToken cancellationToken = default)`. `TranslationService.cs` is sealed, constructor-guards the provider, synchronously guards null request, then calls the provider exactly once with the same request/token and **returns its exact task**. No per-request state, own cancellation source, catches, task wrapper, duplicated Core validation or `ITranslationService`.

`src/FihLens.Infrastructure/Translation/FakeTranslationProvider.cs` supports exact ordinal `Hello world`, English→Vietnamese, Translate mode, and null or valid CEFR level. Keep the [approved fixture](phase-0-application-operation-plan.md#fixed-demonstration-payload) verbatim. For every success create a fresh result and privately owned read-only collection views. Order behavior: null request throws synchronously; already-canceled token returns a canceled task even for an unsupported otherwise valid fixture; support check throws synchronous `NotSupportedException`; default zero latency returns a completed task. Constructor accepts optional `TimeSpan` latency, rejects negative/invalid delay, and the delayed path uses cancelable `Task.Delay`; demo startup supplies one second. Tests control ordering without sleeping.

### Checkpoint 2 — one MVVM demo screen

Add `FihLens.WinUI/ViewModels/MainWindowViewModel.cs`; compile that same source into the existing net10 test project as a linked file, with **CommunityToolkit.Mvvm 8.4.2** pinned in both projects. Use `ObservableObject`, generated async commands and public partial observable properties (not field annotations with WinRT/AOT marshalling risk). Keep Window, controls, DispatcherQueue, provider implementations, HTTP and JSON out of the VM. A single typed get-only `MainWindow.ViewModel` is assigned before `InitializeComponent`; bind live two-way input and one-way result/status/error/busy, plus commands. Startup composes fake → service → VM → window once. Do not add a separate presentation project for one linked VM.

Start with `Hello world`; fixed English→Vietnamese, Translate, null level. The screen has multiline input, Translate/Cancel, progress, status/error, original text, natural translation, explanation, vocabulary, and grammar/alternatives when present. Label demo as supporting only the exact fixture. Use native controls/resources; keyboard operation, selectable long output, scrolling, resizing, readable light/dark themes, accessible labels and text errors are acceptance targets.

VM allows one request: blank/closed/busy prevents Translate; input is snapshotted without trimming; start clears old output/error, disables editing/Translate and shows progress. Cancel requests cooperative cancellation but `IsBusy` stays true until task completion. If a noncooperative provider succeeds after cancel, suppress that result. Requested cancellation is not an error; unexpected cancellation is a failure. Unsupported demo input gets exact-fixture guidance; other failures get safe feedback. On Window.Closed, mark VM closed before requesting cancellation; after that, do not mutate VM-owned result, error, status or busy fields, including `finally`. Generated command completion notifications may still occur. Use existing command cancellation support, with no second `CancellationTokenSource` or blocking UI wait.

### Checkpoint 3 — Gemini and DeepSeek translation

Add `src/FihLens.Application/Translation/{TranslationProviderException,TranslationProviderFailureKind}.cs` as one small UI-safe failure vocabulary: `Authentication`, `RateLimited`, `Unavailable`, `Timeout`, `InvalidResponse`, `Refused`, `RequestRejected`. Preserve inner diagnostic causes where safe; never put credentials, raw headers, input or model bodies in UI/logs by default. Caller cancellation propagates distinctly. Unexpected defects take the VM generic-error path.

In Application, add `Translation/PromptBuilder.cs` with `Build(TranslationRequest)` and concrete `Translation/TranslationInstructions.cs` with `SystemText` and `UserText` fields. The builder expresses shared product instructions and accepts **only** English→Vietnamese, Translate mode, null `UserLevel`; reject other valid Core requests before HTTP. It returns trusted system text separately from the user's unmodified text. Application contains no HTTP or JSON types. In Infrastructure, add `Translation/TranslationParser.cs`, provider-specific adapters `GeminiTranslationProvider` and `DeepSeekTranslationProvider`, and only small private DTO/schema helpers required by real wire contracts. Each adapter calls the Application builder then maps its two fields to its own API roles.

Generated analysis requires nonblank `naturalTranslation`; `vocabulary`, `grammar`, `alternatives` arrays are present and nonnull (empty allowed); optional `explanation`, `context`, `tone` may be absent or null, never wrong type. Vocabulary item camelCase fields: nonblank `word`, `partOfSpeech`, `meaning`; optional `phonetic`, `exampleSentence`. Grammar: nonblank `pattern`; optional `explanation`, `exampleSentence`. Alternative: nonblank `text`; optional `explanation`. Reject null array elements and wrong field types. Ignore unrelated extra fields; set `OriginalText` from the request. The Infrastructure parser validates JSON syntax and semantics before constructing Core records; malformed or unusable content becomes `InvalidResponse` at adapter boundary. No regex extraction, fence stripping, fabricated fields or repair call.

**Provider contract, to be rechecked against the official worksheet before coding:**

| Adapter | Request | Valid completed output |
|---|---|---|
| Gemini | `POST https://generativelanguage.googleapis.com/v1beta/models/gemini-3.5-flash-lite:generateContent`, request-scoped `x-goog-api-key`; `systemInstruction.parts` for trusted guidance and `contents` user text; `generationConfig.maxOutputTokens=2048`; current `generationConfig.responseFormat.text` uses `mimeType: APPLICATION_JSON` and a supported schema subset. Do not mix older/deprecated response fields or Interactions API fields. | No `promptFeedback.blockReason`; exactly one candidate with `finishReason=STOP`; skip thought-marked parts, concatenate remaining ordered text parts into nonempty analysis JSON, reject unsupported nontext parts. Safety/blocklist/prohibited/recitation → `Refused`; max-token, unknown/missing finish or no usable text → `InvalidResponse`. |
| DeepSeek | `POST https://api.deepseek.com/chat/completions`, request-scoped bearer key; model `deepseek-flash`, `thinking:{type:"disabled"}`, system/user messages, `response_format:{type:"json_object"}`, `max_tokens:2048`, `stream:false`. System guidance explicitly mentions JSON and includes desired example. JSON-object mode guarantees syntax only. | Exactly one choice, `finish_reason=stop`, nonblank `message.content`; ignore `reasoning_content`. `content_filter` → `Refused`; `length`/tools/unusable content → `InvalidResponse`; `insufficient_system_resource` or `aborted` → `Unavailable`. |

Shared HTTP policy: one application-lifetime `HttpClient` for the **selected** adapter, with documented `SocketsHttpHandler.PooledConnectionLifetime`; 30-second timeout, `ResponseContentRead`, `MaxResponseContentBufferSize=1_048_576`. Fresh request/response per operation, request-scoped credential, caller token passed to send and read. Startup owns/disposes client only after pending work is complete on explicit process shutdown; Window.Closed requests cancellation but cannot prove completion and must not immediately dispose the client. If final-window process exit is the lifecycle, rely on process teardown, never block UI or claim asynchronous Closed work finishes. Check caller cancellation first; distinguish timeout (including timeout-shaped `OperationCanceledException`), transport/server unavailability, and bounded-response/invalid-content failures. In .NET 10, `HttpRequestException.HttpRequestError == ConfigurationLimitExceeded` maps to `InvalidResponse` without matching exception text; other transport errors map to `Unavailable`. Map documented HTTP statuses: 401/403/402 → authentication/account; 429 → rate limit; 400/404/422 → request rejected; 5xx → unavailable except 504 → timeout. Reject unknown unsuccessful statuses safely. Send at most once; no hidden retry.

At `App.OnLaunched`, read `FIHLENS_PROVIDER_MODE` once. Default `demo`; `gemini` requires only `GEMINI_API_KEY`, `deepseek` only `DEEPSEEK_API_KEY`. Unknown mode or missing **selected** credential shows a clear configuration failure and sends no HTTP; never silently choose fake. Unselected credentials are unnecessary. Label selected provider/mode; tell the user that live input goes to that provider. The development environment must supply its own key; never commit, embed or echo it. A shipped end-user key/account design is outside this milestone.

## Ordered execution and exits

1. **Foundation (G1):** Recheck worktree and Core baseline; add portable graph, service/fake and focused tests. Exit when the new libraries build and service/fake/composed-flow tests pass with exact payload and cancellation/task semantics. This is the first independently reportable checkpoint.
2. **MVVM demo (G2):** Add Toolkit, linked VM source/tests and the one screen; verify portable VM state transitions, then Windows x64 build and demo smoke. Exit when both portable and Windows evidence exist. If Windows is unavailable, label only this platform gate pending and continue independent cloud planning/offline adapter work.
3. **Dual cloud (G3):** Recheck official provider worksheet; implement shared prompt/parser/failure vocabulary, Gemini then DeepSeek request/response adapters and fixture/handler tests; integrate startup mode and safe error text. Exit when both offline adapter suites and startup modes pass, **plus** a separate non-sensitive live smoke for each provider on Windows with configured accounts. No exact model-output text assertion. Credentials unavailable leave the corresponding live gate pending; do not mark full milestone complete.
4. **Integration review (G4):** Re-run affected portable suite once after final changes, Windows build/smoke, check warnings/Toolkit/XAML diagnostics, source/project graph, ownership and safe failure display. Report changed files, per-gate evidence, remaining blockers and the engineering concepts learned: inward dependency, task/cancellation ownership, MVVM UI state, HTTP lifetime, envelope versus domain validation. Stop at this manual translator; defer richer CEFR/learning behavior and later capture/history features.

## Verification and stop rule

The [test specification](test-spec-manual-translator-phase-0-2.md) maps each checkpoint to runnable commands and observable assertions. Portable unit/in-process tests prove deterministic contract behavior; fake HTTP-handler tests prove wire mapping without accounts; Windows x64 smoke proves XAML/bindings/runtime; separate live smokes prove each actual account/API path. Classify each gate as passed, failed or pending with a reason. Do not convert absence of Windows/credentials into a pass. Resolve new attributable warnings. Complete only when all three checkpoint gates and integration review pass, or stop a truly blocked branch with exact evidence while progressing others.
